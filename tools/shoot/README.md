下面是一套"实机窗口直拍 + 合成输入驱动 + ffmpeg 后期"的视频生产线，最初为 `site/` 官网录 Hero 循环，
后来扩展成能录 15 秒独立演示片（输入框聚焦放大、历史压暗、重定时）。

工具：`click` / `mmove` / `typer`（CGEvent 合成输入）、`drag.swift`（把窗口拖到 HiDPI 屏）、
`winbounds.swift`（读窗口号与位置）、`seed_demo_session.py`（演示数据准备/还原）、
`input_grow_build.sh` + `retime_build.sh`（两级成片管线）。

**下面 一拍~十拍 是按时间顺序的拍摄记录**，越靠后越接近当前做法，前面的做法有些已经废弃——
每节里都标注了当时的坑，那些坑仍然有效。

## 构建

```bash
cd tools/shoot
swiftc -O click.swift -o click        # CGEvent 左键点击: ./click <x> <y>
swiftc -O move.swift -o mmove         # 移动光标(不点击): ./mmove <x> <y>
swiftc -O type.swift -o typer         # Unicode 逐字打字: ./typer <文本> <每字符秒>
swiftc -O key.swift -o key            # CGEvent 单键: ./key <keycode> [cmd] [shift]
swift winbounds.swift <pid>           # 列出进程在屏窗口: id/x/y/w/h(无需编译)
```

## 管线（2026-09-20 首次拍摄验证）

```bash
# 1. 备份真实数据
cp ~/Library/Application\ Support/Parrotlet/chat-sessions.json /tmp/backup/

# 2. 写入演示 session(mode:"conversation"=Tutor;summary.title=窗口标题;
#    turns[] 每项需 id/role/content/at/deliveryStatus:"complete"),重启 App

# 3. 点开菜单栏窗口
osascript -e 'tell application "System Events" to tell application process "Parrotlet" to click menu bar item 1 of menu bar 2'

# 4. 查窗口号(重启即变,必须现查)
PID=$(pgrep -x Parrotlet); swift winbounds.swift $PID

# 5. 后台录 25-30s(流式长度不可控,留余量),同时驱动:
screencapture -v -V30 -l<窗口号> take.mov &
sleep 2; ./click <输入框x> <输入框y>
./mmove <窗外x> <窗外y>            # 光标移出窗口,避免 I-beam 入镜
./typer 'question text?' 0.09     # 90ms/字符有打字机感
osascript -e 'tell application "System Events" to keystroke return'

# 6. 抽帧验收(尤其底部条带,检查 "Reply interrupted" 横幅)
ffmpeg -ss 11 -i take.mov -frames:v 1 -vf crop=1018:420:0:1076 tail.png

# 6.5 裁掉窗口阴影黑边(-l 直拍连阴影一起录,四周是纯黑;
#     cropdetect 量出内容矩形,本次为 882x1360+112+76,恰为窗口点数的 2 倍)
ffmpeg -ss 2 -t 4 -i take.mov -vf cropdetect=round=2 -f null - 2>&1 | grep -o 'crop=[0-9:]*'

# 7. 后期(时间轴先 fps=30 归一化,否则 zoompan 慢放 1.9x;
#    zoompan 变量是 time 不是 t;无 clip(),用 min(max(x,0),1) 拼 smoothstep;
#    filtergraph 写文件用 -/filter:v 读入,文件内逗号写 \,)
ffmpeg -ss 0.8 -to 14.0 -i take.mov -/filter:v vf.txt \
  -an -c:v libx264 -preset slow -crf 24 -pix_fmt yuv420p -movflags +faststart hero-loop.mp4

# 8. 还原数据,重启 App
```

## 坑清单

- **别用 AppleScript keystroke 打字**：丢空格（引号邻近必丢），`key code 49` 也不稳。用 `type.swift`（CGEvent + `keyboardSetUnicodeString`）。
- **光标会入镜**：CGEvent 点击后光标停在原地，拍完才发现 I-beam 悬在输入框里。点击后必须移出窗口。
- **窗口尺寸被场景记忆**：`NSWindow Frame chat` 存在 defaults 里，拍摄前 `defaults delete tech.mellivora.language-agent "NSWindow Frame chat"` 重置回 440×680（minAutoHeight=680 是高度下限，内容短不会更矮）。
- **cropdetect 不能跨片复用，也不适合量窗口**：key window 的阴影比非激活大（同一窗口两次录制尺寸差 88px:1016×1496 vs 1104×1584），且阴影是渐变非纯黑，阈值检测本身就偏。正确做法：对当次录制抽帧做像素扫描，找窗口边缘高光线（(70,72,74) 双列，内侧即窗体底色 (33,35,37)）定为内容原点。
- **第一击可能只激活不聚焦**：panel 非 key 时第一次点击只让 panel 变 key（输入框出现光标但不吃键盘事件），typer 整段打字丢进虚空。保险做法：连点两次输入框（间隔 0.5s+）再打字，或在按 return 前 `screencapture -l` 抽静帧确认文字落进输入框。
- **screencapture -v 的 mov 时间戳不可信**：`-ss` 前置 seek 抽单帧会落到错误时间点（相差数秒）。核对时间点一律线性解码（`fps=N,tile=` 拼网格图）；正式转码用 `-ss/-to` 裁剪是准的，但抽帧验收必须对**成品**再线性解码一遍确认。
- **zoompan 时间轴**：源 ~57fps + `d=1 fps=30` = 慢放 1.9 倍。先 `fps=30` 再 zoompan。
- **DeepSeek 流式长度不可控**：同一问题 3s~16s，偶尔截断出 "Reply interrupted"。录长一点，拍完抽帧检查。
- **zoompan 放大锚点要跟内容对齐**：居中锚点 `(iw-iw/zoom)/2` 会把左对齐的打字文字裁掉（1.28x 时左右各裁 ~96px）。打字场景用偏左锚点 `(iw-iw/zoom)*0.1`，右侧装饰性元素出画可接受。
- `afinfo` 读不出 mov 时长尺寸，用 AVFoundation。
- 窗口 441×680pt 录出 1018×1496px（Retina ~2.3x），后期有 ~1.5x 无损变焦余量。

## 二拍（2026-09-21）：hero-loop v2 成片参数

针对首版问题（chrome 噪音/变焦裁字/dip 转场/循环断在流式中/30fps+crf24 发虚/poster 与视频两版 UI）的修正版：

- **拍前**：窗口重置 440×680（见上 defaults delete）；演示 session 加一轮短热身问答（底部锚定的短对话会在窗口顶部留出 250px 空洞）；config `appearance` 临时改 `dark`，拍完连同 sessions 一起还原。
- **录制**：窗口开在 HiDPI 副屏，120fps 直出（1016×1496，内容 880×1360+68+52）。
- **后期裁掉标题栏**（crop y 偏移 +100px @2x）：去掉截断标题/橙色头像/× 按钮，头像暖色与页面单一 #6199f6 色系不再打架。
- **不做变焦不做 dip**：运动全部来自内容（打字/滚动/流式）。
- **节奏**：淡入 0.25s 后立刻开打字（55ms/字符）→ 发送 → 流式 → 完整回答**稳定停留 2.4s** → 淡出 0.5s；首尾都是稳定态，循环接缝读作「重播」而非断片。成品剪在流式完成后 ~2s 内，顺便避开 summary 写回引发的单帧重建闪烁（本条约在成片 14s 处，剪掉了）。
- **编码**：`fps=60, scale=760:-2, crf 19, preset slow, yuv420p, +faststart`，8.1s ≈ 630KB。
- **poster**：从源片起始构图同管线（同 crop/scale）抽帧另存 `hero-poster.png`，别复用旧静态截图（UI 版本不同会闪跳）。
- 转码命令：`ffmpeg -ss <in> -to <out> -i take.mov -vf "crop=880:1260:112:176,fps=60,scale=760:-2,fade=t=in:st=0:d=0.25,fade=t=out:st=<dur-0.5>:d=0.5" -an -c:v libx264 -preset slow -crf 19 -pix_fmt yuv420p -movflags +faststart hero-loop.mp4`（crop 的 112/176 是 key-window 阴影布局下的实测内容原点 112,76 + 标题栏 100；换机器/重录必须重新像素扫描，别照抄）

vf.txt 参考（推轨 1→1.28x→1，首尾淡入淡出；crop 值来自 cropdetect，不同窗口尺寸要重测）：

```
crop=882:1360:112:76,fps=30,zoompan=z=1+0.28*(pow(min(max((time-1.3)/1.2\,0)\,1)\,2)*(3-2*min(max((time-1.3)/1.2\,0)\,1))-pow(min(max((time-6.0)/1.6\,0)\,1)\,2)*(3-2*min(max((time-6.0)/1.6\,0)\,1))):x=(iw-iw/zoom)/2:y=(ih-ih/zoom):d=1:fps=30:s=760x1172,fade=t=in:st=0:d=0.3,fade=t=out:st=12.6:d=0.5
```

## 三拍（2026-09-21）：15 秒独立演示片

给产品录一条 15s 独立 demo（不是官网 hero 循环）。成片 `assets/video/language-agent-demo-15s.mp4`（整窗 880×1360）与 `-clean.mp4`（裁掉标题栏 880×1260，同二拍构图）。

- **窗口每次重启都要重新拖到 HiDPI 屏**：app 恢复的是 defaults 里的 frame，重启后落在主屏（3440×1440 非 Retina，直拍只有 1x，成片发糊）。`defaults write` 改 frame 会被 app 夹回主屏，只能开窗后用 `drag` 拖过去：
  `swiftc -O drag.swift -o drag` → `./drag <起x> <起y> <到x> <到y> 90`（起点取标题栏中部，终点 x ≥ 3440 即落到副屏）。
- **scroll 事件会把真实光标 warp 过去**：当时写的 `scroll.swift`（已删）只设 scrollWheel 事件的 `location`、不发 mouseMoved，但 macOS 依然把物理光标移到该坐标（实测 `NSEvent.mouseLocation` 跟着变），所以**滚动镜头光标必入镜**，`screencapture -v` 也照拍。本片第二拍最终没用滚动，运动全部来自打字与流式。
- **演示数据 `summarizedTurns` 要写成当前轮数**：`shouldSummarizeMidChat` 的门槛是 `turns.count - summarizedTurns >= 5`，写 0 会在回复落地后立刻触发后台总结，标题当场改名，成片里读作闪一下。写成与 `turns.count` 相等即可不触发。
- **节奏（15.0s）**：淡入 0.3s → 静止 ~0.9s → 打字（82 字符、90ms/字符 ≈ 8s）→ 停 0.6s → 回车 → 流式 ~1.3s（conversation 模式 361 字）→ 静止收尾 → 淡出 0.5s。DeepSeek 流式比预期快（~250 字/秒），15s 里打字占大头，别指望靠流式填时长。
- **取景**：窗口 440×680pt @2x 录出 1104×1584（连窗口阴影一起录），cropdetect 量出内容矩形 `crop=880:1360:112:76 `；裁标题栏把 y 再 +100。
- 转码：`ffmpeg -ss 0.6 -t 15.0 -i take.mov -vf "crop=880:1360:112:76,fps=60,fade=t=in:st=0:d=0.3,fade=t=out:st=14.5:d=0.5" -an -c:v libx264 -preset slow -crf 19 -pix_fmt yuv420p -movflags +faststart <out>.mp4`

## 四拍（2026-09-21）：light 模式 + 两拍结构

同一条 15s 片子的第二版：**light 模式** + 把一次长打字拆成**两拍**（批改 → 追问解释）。

- 成片：`assets/video/language-agent-demo-15s-light.mp4`（整窗 880×1360）/ `-light-clean.mp4`（裁掉标题栏 880×1260）。
- **`type.swift` 的真实开销是 interval + ~22ms/字符**，不是源码里那个 8ms。实测 interval 0.055 打 70 字符用了 5.4s（77ms/字符）。排期按 `字符数 × (interval + 0.022)` 算。
- **发送后输入框保持焦点**：`canSend` 只在 `streamingText != nil` 时禁用发送按钮，输入框本身没有 disable，所以两拍之间不用再点一次输入框（省掉了"光标入镜"的风险）。但**回车必须等流式结束再按**，否则 `canSend == false` 会被直接吞掉。
- **CJK 可以直接用 `typer` 打**（`keyboardSetUnicodeString` 绕过 IME），24 字中文追问落字正确，不用切输入法。
- 实测时间分布：第一段打字 5.4s / 批改流式 0.7s / 读批改停顿 1.8s / 第二段打字 1.4s / 等首字+流式 2.5s / 收尾 1.5s / 淡入淡出 0.9s。打字占比从上一版的 57% 降到 45%，流式从 5% 升到 13%。
- light 模式成片体积约 1.6MB，同参数 dark 版 0.99MB——浅色画面细节多，同 crf 下码率更高，必要时 crf 提到 21。

## 五拍（2026-09-21）：聚焦效果

给 light 两拍版加聚焦，解决"整屏平、观众不知道看哪里"。成片 `assets/video/language-agent-demo-15s-light-focus.mp4`（整窗）/ `-focus-clean.mp4`（裁标题栏）。

**先说结论：这个 UI 不能靠裁剪推近来聚焦。** 对话内容横向铺满 880px（气泡约 40..840），zoompan 是等比裁剪——1.06x 就已经左右各切掉 25px，再大就切字。所以聚光只能靠**明暗对比**，推近只能做到 1.055x 的"轻推"。

三层效果：

1. **历史渐隐（主力）**：历史文字向白场淡出到约 50% 对比（`lutrgb=val*0.55+115`），当前轮保持满对比；边界随时间上移/下移跟随当前轮——打字段收到输入卡，流式段往上开。实现是一张 8×1360 的竖向遮罩序列（900 帧 gray8），`scale=880:1360` 拉伸后 `alphamerge` 挂到淡出版本上，再 `overlay` 回原片。遮罩必须按**行主序**写（`buf += bytes((v,))*W`）；写成列主序会得到周期性错位的乱遮罩，症状是"该清晰的地方也被淡掉了"。
2. **输入卡脉冲**：蓝 #6199f6 柔光描边，在两次打字前各脉冲一次（t=0.25 / 8.85，各 0.5s）。真实光标不能入镜，这是画面里唯一的"手在这里"提示。峰值 alpha 0.20、σ=9；调到 0.42 就变成浏览器 focus ring 了。
3. **切点式推近**：zoompan `z=1.00↔1.055`，四段 smoothstep，锚点 `x=(iw-iw/zoom)*0.35`、`y=(ih-ih/zoom)*0.85`（偏左下，内容在下方且左对齐）。全程只有 5.5% 推近量，作用只是让画面不静止。

- 一键复现（**该脚本已删**，逻辑已并入 `input_grow_build.sh` 的历史压暗层，仅作记录）。
- ffmpeg 坑：homebrew ffmpeg 9.0.1 **没有 `-filter_complex_script`**，filtergraph 得用 `$(cat fg.txt | tr -d '\n')` 传进去；文件里的函数参数逗号必须写成 `\,`，否则被当成滤镜分隔符。
- 体积：只做渐隐+脉冲约 1.6MB；叠加 zoompan 后约 2.7MB（重采样让细节变多）。

## 六拍（2026-09-21）：双画幅剪辑（真正的「推近」）

五拍的 zoom 只有 5.5%，实测在焦点区每帧位移 <0.4px —— 完全看不见。原因不是幅度调小了，而是**这套 UI 根本不能等比放大**：文字横向占窗口 91%（气泡 x 40..840 / 880），等比放大到 1.10x 就切字；不动点又正好落在输入卡上。详见 README 末尾「为什么 zoom 不可见」。

改法：**不放大，把全景缩小。** 同一条 take 出两种取景，切在一起：

- **全景**：整窗 880×1360 缩到 `0.96·H` 高，居中放在 `880×H` 画布上（底色 #EDEFF3，窗口用圆角遮罩抠出来）
- **近景**：从窗口底部裁 `880×H`，1:1 铺满画布
- **切点**：0.70s 全景→近景，6.00s 回到全景（发送+滚动那段需要大视野），7.60s 再切近景

**推近感 = 1360 / (0.96 × H)** —— 这就是你手里的旋钮，画布越矮推近越猛，且全程零裁字、零分辨率损失（近景永远是 1:1 原始像素，被牺牲的只有全景）。

| 画布 | 推近感 | 近景裁切 | 代价 |
| --- | --- | --- | --- |
| 880×1000 | 1.42x | y 360..1360 | 用户的追问气泡仍在画面内 |
| 880×950 | 1.49x | y 410..1360 | 追问气泡贴到画幅上沿 |
| 880×900 | 1.57x | y 460..1360 | 追问气泡被切出画外 |

- **近景高度的下限 ≈ 900**：实测回答最早出现在 y≈497，`1360-H > 497` 就会切掉回答顶部。想更猛只能让近景做平移（crop 的 y 支持 `t` 表达式，已验证可用）。
- 一键复现（**该脚本已删**，方案被「输入框聚焦变大」取代，仅作记录）。
- 圆角遮罩：窗口内容框（cropdetect 给的 880×1360）四角是**纯黑**（圆角外侧），直接缩放会在浅色画布上留下四个黑角。用一张 880×1360 的圆角 PGM（半径 30px，1px 抗锯齿）`alphamerge` 抠出来解决。
- 120fps 源在这里又派上用场：全景缩小 0.6~0.7 倍是降采样，抗锯齿足够；如果当初用 60fps 录，缩放质量会差一截。

## 七拍（2026-09-21）：输入框「聚焦变大」（后期合成，A 方案）

需求：聊天窗完全不动，输入框在**敲下第一个字符**时**整体等比放大**（带光晕、带动画），并且**浮层溢出**聊天窗边界。

**结论：录屏直出做不到**（app 里没这个行为，而且窗口直拍拍不到窗口外面——`screencapture -l` 的窗口外圈是纯黑）。**后期合成能跑通**，成片 `assets/video/language-agent-input-grow-demo.mp4`（1080×1420）。

做法：输入卡在录屏里是**固定矩形**（实测 838×162 @ 内容坐标 20,1166），所以可以精确抠出来等比放大再贴回去。

**放大锚点 = 输入卡的左下角**（左边和下边不动，往右上撑开）：

| | 1.0x | 1.2x |
| --- | --- | --- |
| 卡片尺寸 | 838×162 | 1006×194 |
| 左边界 | 20 | **20（不动）** |
| 下边界 | 1328 | **1328（不动）** |
| 右边界 | 858 | 1026（**溢出窗口右边 146px**） |
| 上边界 | 1166 | 1134（往上撑） |

实现上就是两处改动：`pad=1006:194:0:32`（卡片贴放大画布的左下角，不是居中），`zoompan=x='0':y='ih-ih/zoom'`（裁剪窗锚在左下）。验证方法：把 z=1.0 和 z=1.2 各渲一帧做差分，差异包围盒的 x 最小值应当正好等于卡片左边界（实测 x 从 80 起 = 窗口 60 + 卡内边距 20 ✓）。

| 环节 | 结论 |
| --- | --- |
| 逐帧改缩放 | ffmpeg `scale=...:eval=frame` **不行**——实测 30 帧输出尺寸全锁死在第一帧 |
| 可行替代 | `pad` 到目标画布（1006×194）+ `zoompan` 把 `z` 从 1.0 缓动到 1.2；红块实测 838→1004px 动画正常 |
| 时间变量 | zoompan 里是 `time` 不是 `t`（写 `t` 报 Undefined constant） |
| 一个 label 两个消费者 | **必须 `split=2`**。卡片 alpha 要同时喂 alphamerge 和光晕，直接复用会报 "Input frame sizes do not match (1006x194 vs 1104x1584)"，极具误导性 |
| 黑角 | 内容框 880×1360 的四角是纯黑（窗口圆角外侧），贴到浅色画布上会露黑三角，要用 880×1360 圆角遮罩 `alphamerge` 抠掉 |
| 光晕 | 卡片 alpha → `boxblur=12` → `lut=y='val*0.34'` 当 alpha，配 #6199f6 实色 `alphamerge`，垫在卡片底下 |

**时间轴**（打字开始放大、发送瞬间缩回，两拍各一次）：

| t | 动作 |
| --- | --- |
| 0.40→0.72 | 1.00x → 1.20x（第一拍打字） |
| 5.92→6.12 | 1.20x → 1.00x（发送） |
| 9.05→9.37 | 1.00x → 1.20x（第二拍打字） |
| 11.30→11.50 | 1.20x → 1.00x（发送） |

一键复现：`./input_grow_build.sh <take.mov> <ss> <out.mp4>`，产出 sha256 可复现。

**还没做的（等背景细节定了再加）**：桌面壁纸（现在是 #EDEFF3 占位色）、卡片投影在抠图时被裁掉、窗口自身的投影。**最重要的一条**：这是"演示了 app 还不具备的行为"，不是实拍，文案上要么回避要么先把 app 做了。

### 修正：输入卡是「内容驱动高度」，不能写死裁切框

**症状**：单行输入时正常；输入折成两行后放大，卡片顶边把上面那条消息的最后一行**从中间切开**，同时卡片自己的上内边距消失、文字贴着顶边。

**根因**：输入卡的高度跟着内容变——单行 **163px**、两行 **196px**（底边不动，顶边上移 33px）。原实现用写死的 `crop=838:162:20:1166`（单行几何），到两行状态就从卡片内部 34px 处开始裁，所以卡片顶部被切掉、贴回去的顶边落进了上面那条消息里。

**改法**：两条平行链路，各自用正确的裁切几何，再按时间硬切。

| 状态 | 卡片（内容坐标） | 放大画布 1.2x | pad | overlay 位置 |
| --- | --- | --- | --- | --- |
| 单行 | 838×162 @ (20,1166) | 1006×194 | `1006:194:0:32` | (80,1164) |
| 两行 | 838×196 @ (20,1132) | 1006×235 | `1006:235:0:39` | (80,1123) |

切换点（成片时间）：**4.35s 进两行 / 5.95s 回一行**（take 实测 4.85 / 6.45，减 0.5 的 `-ss` 偏移）。两处切换实测平滑。

**过程中又踩了两个坑，都比表面症状隐蔽：**

1. **卡片不能从"已经 alphamerge 过的窗口"里裁。** 从带 alpha 的窗口裁出来的卡片再 alphamerge，alpha 会被破坏，overlay 就把该透明的地方画成**不透明黑**——表现为卡片四周一圈黑边、原卡片从底下透出来。必须从**原始窗口**分流出来裁。
2. **每种卡片高度都要有同尺寸的圆角遮罩。** 用 838×162 的遮罩去配 838×196 的卡片，底部 34px 的 alpha 是 0，原卡片会**重影**透出来。

回归检查：叠卡后 (70,1200) 应是窗口白、(1000,1200) 应是放大卡片的白、(1120,700) 与四角应是画布灰 #EDEFF3；任一处变黑/变白说明 alpha 坏了。

### 修正二：放大时给上面的内容「让位」（B 方案）

上一版修好了卡片自身几何，但还剩一个：两行卡片放大后顶边到画布 **y=1123**，而上一条消息第 2 行在 **1141..1161** —— 整行被盖掉。

**做法**：放大时把列表内容整体**上移 39px**（= 原卡片顶边 1162 − 放大后顶边 1123），模拟真实 app 里列表被输入框挤上去。

| | 值 |
| --- | --- |
| 新 viewport（画布） | 130..1123（标题栏下沿 → 放大后卡片顶边），993px |
| 要裁的源区段（画布） | 169..1162 → 内容坐标 **139..1132** |
| 上移量 | 39px |
| 上移后消息第 2 行位置 | 1102..1122（卡片顶边 1123，不重叠） |

关键点：源区段的末尾 1162 **正好等于原卡片顶边**，所以不会把卡片像素带进列表；上移 39px 后列表顶部会裁掉 39px（读作"列表滚上去了"，符合真实行为）。

实测（画布 y，两行状态）：

| | 上一条消息两行 | 卡片文字 |
| --- | --- | --- |
| 不让位 | 只有第 1 行（1097..1122），**第 2 行丢失** | 1159..1231 |
| 让位后 | 1059..1085 / **1103..1122**（两行都在） | 1159..1231 |

切换点仍是 4.35s / 5.95s，与卡片换几何、app 自身重排同时发生。

### 修正三：列表源必须取自「折行前」的帧

让位之后发现还剩 6px：上一条消息第 2 行**下缘（y 的尾巴）被压平了**。查源片确认——**是 app 自己压的**：折行时卡片顶边从 1165 升到 1132，正好盖掉那行底部 6px（`1111..1137` → `1111..1131`）。

用当前帧的像素救不回来，所以多接一路**滞后 2s** 的输入当列表源（那时卡片还是单行，那行完整）：

| | 值 |
| --- | --- |
| 列表源 | 滞后 2s 的 take，crop 内容 y **145..1137**（capture y 221，993 行） |
| 上移量 | **45px**（内容 c → 画布 130+(c−145)） |
| 上移后第 2 行 | 画布 1097..1122（卡片顶边 1123） |

实测（画布 y）：

| | 第 2 行字形范围 | 下缘 |
| --- | --- | --- |
| 用当前帧（修正前） | 1103..1122（20 行） | **切平** |
| 用滞后帧（修正后） | 1097..1122（26 行） | **完整**（参考：未裁切时 27 行） |

`setpts=PTS+2/TB` 加 `tpad=start_duration=2:start_mode=clone` —— 后者是把 0~2s 补上，否则 overlay 的 `shortest=1` 会让整条链从 2s 才开始。

### 又踩一个坑：`-ss` 之后直接 `fps=60` 会少帧

### 一级新增：历史压暗（之前重写管线时丢了）

内容坐标的边界 KEYS（上方淡出、下方满对比），边界随时间跟着当前轮走：

| t | 边界 y | 说明 |
| --- | --- | --- |
| 0.00–6.05 | 930 | 打字段：只留输入卡 + 上一条助教消息 |

### 修正四：光晕重做（原来根本没显示）

**症状**：输入框放大后四周是干净的硬边，没有任何光晕——之前几版一直以为有。

**根因**：光晕遮罩直接拿的是卡片自身的 alpha（1006×194 / 1006×235）。但放大态下卡片**正好填满整张画布**，`boxblur` 没有"外面"可以扩散，blur 完还是实心矩形，再被卡片盖住 → 等于没做。

**改法**：给光晕单独一张**比卡片大一圈**的画布。

| 项 | 单行链 | 两行链 |
| --- | --- | --- |
| 卡片画布 | 1006×194 | 1006×235 |
| 光晕画布 | **1086×274**（四周各留 40） | **1086×315** |
| 遮罩处理 | `pad=1086:274:40:40:color=black,boxblur=20:2,lut=y='val*0.45'` | 同构 |
| overlay 位置 | (40,1134) | (40,1093) |

**验证**：沿卡片右边界向外扫一行，底色 b−r 从 +9（桌面灰）升到 **+30**，光晕向外延伸约 24px；
改之前这条线上全是 +9，与桌面底色完全一致（= 没有光晕）。

> 光晕是垫在卡片**下面**画的，所以会同时溢到窗口内的消息区和窗口外的桌面上——这是想要的效果。

### 修正五：四项细节（回弹 / 让位动画 / 投影 / 片尾微动）

| # | 项 | 做法 | 验证 |
| --- | --- | --- | --- |
| 1 | **放大加回弹** | 放大用 easeOutBack（过冲到 1.1 再收回），缩回仍用 smoothstep；放大画布按**峰值 1.22x** 开（1022×198 / 1022×239），否则 z>1.20 会把卡片边缘裁掉 | 卡片右边界：1072 → **1101（过冲）** → 1085（落位） |
| 2 | **让位动画化** | 动画**裁切 y**（140→185，0.18s smoothstep），overlay 固定 (80,140)。**不能动画 overlay 的 y**——那样过渡中会露出一段未位移的内容形成接缝 | 列表首行 y 从 161 平滑上移到 145 |
| 3 | **卡片加投影** | 从卡片 alpha 再 pad 出 1102×278（/319）画布，`boxblur=28:2`、alpha 0.32、偏移 (+10,+16)；顺序改成 **光晕 → 投影 → 卡片**（原来投影在光晕下面，被完全盖住） | 卡片下方亮度比改前**暗 7–13 级** |
| 4 | **片尾加微动** | 最后一段（读答案）叠一个 `zoompan` 极慢推近 1.00→1.07 | 窗口左边缘 1.1s 内从 x=61 移到 x=40；**片尾再没有 ≥0.4s 的静止段** |

**结果**：静止从 5.3s 降到 **4.1s**，且**没有任何 ≥0.4s 的静止段**；打字 5.2s、大动作 5.6s。

> 坑：`crop` 的时间变量是 **`t`**，`zoompan` 才是 **`time`**。混用会报 "Undefined constant"。

## 十拍（2026-09-21）：真桌面 → 设计底 → 透明 alpha

上官网后暴露的问题：**真实桌面壁纸的颜色永远对不上页面的渐变+极光背景**，在深色页面上读成一块亮斑。
实测 hero 那块页面底色是 `#1b1a39`(上) → `#242150`(下)，而视频用的是 Space Gray 壁纸 `#BEBFC4`——差得离谱。

改法经历了三步：

1. **设计底**：按页面实测色生成背景（`brandbg.ppm`，垂直渐变 + 右上柔光），窗口从录制里抠出来，
   桌面像素丢弃。能消掉“亮斑”，但纯色矩形跟页面动画极光之间仍有**可感知接缝**。
2. **透明 alpha**：窗口/卡片直接浮在页面背景上，接缝为零。第一版误判“ffmpeg VP9 不能带 alpha”，
   实际是解码姿势错了：普通解码输出 `rgb24/yuv420p` 会丢 alpha，必须显式 `-pix_fmt rgba`。
   编码参数是 `-c:v libvpx-vp9 -pix_fmt yuva420p -auto-alt-ref 0`；浏览器端优先 `<source type="video/webm">`。
   兜底 MP4 保留同色 RGB，alpha 被忽略时也不会露黑底。
3. **透明版额外加窗口落影**：透明底上窗口如果还是平的会飘；把窗口圆角 alpha pad 大一圈后 blur，
   alpha 0.45 左右，垫在窗口下面。

- 也试过 `mix-blend-mode: screen/lighten` 让黑板融进页面——**不行**：窗口里的深色正文会被背景色染上紫调。
- 踩坑：**压暗遮罩不能当窗口 alpha 用**。第一版把 880×1360 的历史压暗遮罩直接喂给窗口的 alphamerge，
  结果窗口下半截（遮罩值为 0 的区域）被整块抠掉。正确顺序是：裁窗口 → 用压暗遮罩做混合 → 最后套窗口圆角 alpha。
- 踩坑：**透明版淡入淡出要淡 alpha**（`fade=...:alpha=1`）。淡 luma 会把窗口慢慢染黑。
